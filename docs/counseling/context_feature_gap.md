# 컨텍스트 기능 대조: legacy DailyContext → MindriumContextBuilder

legacy `daily_context.dart` 를 폐기하기 전에, 그 안에 있던 "주차별로 어떤 정보를
상담에 보여주려 했는가"라는 제품 의도를 현재 `MindriumContextBuilder` 와 대조한 기록.

legacy 는 주차별로 서로 다른 데이터 소스를 골랐다.

| 주차 | legacy 가 고른 소스 | 현재 상태 |
|---|---|---|
| 1 | `relaxationTasks` 2건 | ✅ 이완 기록을 읽는다 (단, **효과가 확인된 것만** 남긴다) |
| 2 | `diaries` (activatingEvents 있는 것) 2건 | ✅ 일기 요약을 읽는다 |
| 3–4 | `customTags` 중 type 이 `B` 로 시작하는 것 3건 | ⚠️ **부분** — 일기의 belief 칩은 읽지만 독립 custom tag 는 읽지 않는다 |
| 5–6 | `habits` 2건 | ❌ **누락** — 7주차 생활 습관 계획을 읽지 않는다 |
| 7 | `screenTime` | ⛔ **의도적 미사용 후보** — 아래 참조 |
| 8 | `surveys` 2건 | ❌ **누락** — GAD-7 등 설문 점수를 읽지 않는다 |

## 누락과 미사용을 구분한다

legacy 가 읽던 것을 지금 읽지 않는다고 해서 전부 "고쳐야 할 누락" 은 아니다.
데이터가 있다는 이유로 상담 모델에 넣는 것은 최소 필요 데이터 원칙에 어긋난다.

- **누락** — 상담에 쓸 임상적 근거가 있고 아직 구현하지 않은 것
- **의도적 미사용** — 근거가 확보되지 않아 넣지 않기로 한 것

### 스크린타임: 의도적 미사용 후보

`screenTime` 은 상담 개인화에 쓸 임상적 근거가 아직 확보되지 않았다. 사용 시간을
상담 대화에서 언급하는 것이 치료적으로 어떤 이득을 주는지 정해지기 전에는 모델
입력에 넣지 않는다. 넣기로 한다면 임상팀의 판단과 그 근거를 여기에 먼저 적는다.

## 남은 작업

`MindriumDataSource` 에 소스를 추가하는 것으로 확장할 수 있다. 인터페이스가 이미
분리되어 있어 `MindriumContextBuilder` 의 선택·정규화 로직은 그대로 둔 채
소스만 늘리면 된다.

| 순위 | 대상 | 근거 | API |
|---|---|---|---|
| 1 | 설문 (GAD-7) | 8주차 회고에서 직접 쓰인다. 단 챗봇은 점수를 **해석하지 않는다**(`week8_gad7_01`). 사실 확인 수준으로만 다룬다 | `survey_api` |
| 2 | custom tags / 인지 기록 | 3–4주차 자동사고 작업의 재료. 일기 belief 칩과 겹치지만 독립 기록도 있다 | `custom_tags_api` |
| 3 | 생활 습관 계획 | 7·8주차에서 "계획한 행동을 실천했는지" 대화에 쓰인다 | `week7_api` |
| — | 스크린타임 | 의도적 미사용. 위 참조 | `screen_time_api` |
